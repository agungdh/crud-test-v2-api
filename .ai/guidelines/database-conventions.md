# Database Conventions

This project runs on PostgreSQL only. Every migration, model, and API response follows the conventions below so timestamps, public identifiers, audit trails, and soft deletes stay consistent.

## Timezone

- Application timezone and database session timezone must both be `Asia/Jakarta`.
- `APP_TIMEZONE=Asia/Jakarta` and `DB_TIMEZONE=Asia/Jakarta`.
- Laravel sends `DateTime` bindings as `Y-m-d H:i:s` without an offset, so the app timezone and the PostgreSQL session timezone must match. A mismatch shifts every `timestamptz` value.
- API dates stay in UTC ISO-8601 (`...Z`); the frontend converts them to WIB.

## Timestamp columns

| Use case | Method | Never |
| --- | --- | --- |
| Single datetime | `timestampTz()` | `timestamp()` |
| `created_at` / `updated_at` | `timestampsTz()` | `timestamps()` |
| Soft delete | `softDeletesTz()` | `softDeletes()` |
| Date only | `date()` | `timestampTz()` |

- Every datetime column in an application table is `timestamptz`.
- Framework queue tables (`jobs`, `job_batches`) keep their Unix epoch integer columns because the queue worker compares integers. Do not convert them.
- `failed_jobs.failed_at` is an exception inside the framework tables and uses `timestampTz()`.

## Public identifier (`uuid`)

- The primary key stays `id` (bigint). It is never exposed to the frontend.
- Every API-exposed table has a `uuid` column of type `uuid`, generated as UUID v4.
- UUIDs are generated by the `HasUuid` model concern, never by the database. Do not use `WithoutModelEvents` or `withoutEvents()` on models that need a UUID.
- The `uuid` index is a non-unique hash index:

```php
$table->uuid('uuid');
$table->index('uuid', 'users_uuid_hash_index', 'hash');
```

- Route model binding uses the UUID because `HasUuid` returns `uuid` from `getRouteKeyName()`.
- API Resources expose `uuid` and never `id`.

## Foreign keys

- Database columns keep the numeric form: `user_id`, `post_id`, referencing `id`, with the usual foreign key constraint.
- Requests and responses use the UUID form: `user_uuid`, `post_uuid`.
- Form Requests validate the UUID with an existence rule that ignores soft-deleted rows:

```php
'user_uuid' => ['required', 'uuid', Rule::exists('users', 'uuid')->whereNull('deleted_at')],
```

- Services resolve the UUID to the numeric id before writing. Controllers never resolve it.
- Responses expose `user_uuid`, never `user_id`.

## Audit columns and timestamps

- Every application table has the audit columns `created_by`, `updated_by`, and `deleted_by`, plus `created_at`, `updated_at`, and `deleted_at`.
- Add all of them with the project blueprint macro instead of repeating the columns in every migration:

```php
$table->timestampsWithAudit();
```

- The macro is registered in `AppServiceProvider::boot()` and expands to:

```php
$table->unsignedBigInteger('created_by')->nullable();
$table->unsignedBigInteger('updated_by')->nullable();
$table->unsignedBigInteger('deleted_by')->nullable();
$table->timestampsTz();
$table->softDeletesTz();
$table->index('deleted_at');
```

- The `_by` columns are nullable `bigint`, the same type as `id`, and are audit columns, not relations. Do not attach `constrained()` or any foreign key constraint.
- The `HasAuditColumns` concern fills them from `Auth::id()`: `created_by` and `updated_by` on create, `updated_by` on update, `deleted_by` on soft delete, and clears `deleted_by` on restore.
- They stay null for console and queue work because no actor is authenticated.
- Mass deletes through the query builder (`Model::where(...)->delete()`) skip model events and leave `deleted_by` null. Use `Model::delete()` on an instance for audited models.
- Audit columns are database-only. Never expose `created_by`, `updated_by`, `deleted_by`, `created_at`, `updated_at`, or `deleted_at` in API Resources or any response.
- Do not use audit columns as application data either: no ordering, filtering, or decisions on `created_at`; order by the primary key for insertion order. When the app needs a meaningful timestamp, add its own column, such as `submission_time`.
- `HasAuditColumns` hides all six columns from model array and JSON serialization. A Resource that lists them explicitly still leaks them, so keep them out of `toArray()`.

## Soft deletes

- Soft-deletable models use the `SoftDeletes` trait. `timestampsWithAudit()` already adds `softDeletesTz()` and the `deleted_at` index, so the default `whereNull('deleted_at')` filter stays fast.
- Unique columns that should be reusable after a soft delete use a partial unique index instead of `unique()`:

```php
DB::statement('create unique index users_email_unique on users (email) where deleted_at is null');
```

- Restoring a record can fail when the partial unique index conflicts with an active record. Handle that failure explicitly instead of skipping it.

## Model baseline

Every API-exposed model uses the three concerns:

```php
use App\Models\Concerns\HasAuditColumns;
use App\Models\Concerns\HasUuid;
use Illuminate\Database\Eloquent\SoftDeletes;

class Post extends Model
{
    use HasAuditColumns, HasUuid, SoftDeletes;
}
```

## Profile tables (one-to-one with users)

- Credentials stay in `users`; profile data lives in its own table, such as `pegawai`. `users` keeps no display name. User accounts are created, updated, and soft-deleted through the profile CRUD, so every user owns exactly one profile.
- A profile table has a required `user_id` with `restrictOnDelete()` and a partial unique index on `user_id` where `deleted_at is null`, so a user has at most one active profile.
- Derived login identifiers are synced by the Service whenever their source column changes; for example `users.username` always mirrors `pegawai.nip`.
- Deleting the profile soft-deletes its user in the same transaction. The FK stays `restrict` so an accidental hard delete is rejected.
- Case-insensitive unique checks are validated with an explicit `lower(column) = lower(?)` rule, because `Rule::unique()` compares the raw column first; the partial unique index is a backstop, not the user-facing message.

## Search indexes

- Case-insensitive prefix search uses a functional btree index with a pattern operator class:

```sql
create index pegawai_nama_lower_index on pegawai (lower(nama) text_pattern_ops) where deleted_at is null;
```

- A `lower(column)` btree index only serves prefix patterns (`like 'kata%'`). Substring searches (`like '%kata%'`) cannot use it; add a `pg_trgm` GIN index if those must stay fast.

## Tests

- The suite runs against PostgreSQL, not SQLite, so hash indexes and `timestamptz` behavior are verified.
- Schema coverage asserts every timestamp column uses a time zone, the UUID hash index exists without a unique constraint, `deleted_at` is indexed, and the audit columns match the primary key type.
- Feature coverage asserts UUID v4 generation, audit values on create, update, delete, and restore, and that the numeric `id` and audit columns are absent from API responses.
